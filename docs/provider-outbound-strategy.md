# Provider outbound strategy

This document records the outbound mail strategy for v1.2 **provider import
mode**. It extends [provider-import-architecture.md](./provider-import-architecture.md)
for the case where Gmail or another provider remains the public mailbox edge,
while hail still reads and writes visible mail state through local Stalwart/JMAP.

The goals are:

- preserve Stalwart as the local source of truth for the hail UI;
- use the provider's established outbound reputation when the operator has no
  self-hosted SMTP deliverability path;
- avoid duplicate sent messages when the provider also creates a sent copy;
- keep outbound retries restartable without turning provider import into
  bidirectional mailbox sync.

## Decision summary

1. **Use Stalwart submission and a provider smarthost first.** In provider import
   mode, hail should keep building outbound MIME and creating local sent state
   through the existing Stalwart/JMAP path. Stalwart then relays to the
   provider's SMTP submission endpoint as a smarthost.
2. **Use Gmail API send only as a fallback/provider-specific sender.** Gmail
   `users.messages.send` is reserved for accounts where SMTP smarthost relay is
   unavailable, unreliable, or cannot satisfy provider policy. Enabling it adds
   the `gmail.send` OAuth scope but must not add broad Gmail mutation scopes.
3. **Stalwart sent state is authoritative for hail.** The thread and Sent view
   shown by hail come from Stalwart. A provider-created sent copy is an external
   artifact to dedupe/import or ignore, not a second source of truth.
4. **Provider outbound does not imply bidirectional mailbox sync.** Sending may
   use SMTP/API egress, but archive/delete/read/label changes in hail still do
   not mutate Gmail/provider in v1.2. Hail must not request `gmail.modify` or
   broad Gmail scopes merely to keep provider labels/read/delete/archive state in
   step with local Stalwart state.
5. **Every outbound operation has an idempotency key.** Retries must converge on
   one local sent object and at most one provider delivery attempt that hail
   considers successful.

## Preferred path: Stalwart smarthost

```text
hail SPA
  -> hail-api composer endpoint
  -> Stalwart JMAP Email/submission or equivalent local send primitive
  -> Stalwart local Sent object
  -> provider SMTP submission smarthost
  -> recipient MX

Provider mailbox
  -> optional provider-created Sent copy
  -> provider importer/dedupe
  -> either map to the existing local sent object or skip as duplicate
```

Why this is first:

- it preserves the existing hail composer boundary: the browser still talks only
  to `hail-api`, and hail still constructs/sanitizes MIME server-side;
- Stalwart remains responsible for local mail identity, Sent mailbox membership,
  threads, blobs, and delivery/submission state;
- operators can use the same provider SMTP submission path that normal mail
  clients use, including provider DKIM/SPF/reputation handling;
- no Gmail OAuth send scope is required for the initial outbound path.

The smarthost path is also the cleanest multi-provider baseline. Gmail, Fastmail,
Microsoft 365, and other providers commonly expose SMTP submission even when
API-specific send behavior differs.

## Fallback path: Gmail API send

```text
hail SPA
  -> hail-api composer endpoint
  -> Stalwart local Sent object + outbound intent in hail.db
  -> Gmail API users.messages.send(raw RFC822)
  -> recipient MX and Gmail-created Sent copy
  -> provider importer/dedupe maps or skips Gmail Sent copy
```

Use Gmail API send only when the account is configured for it. It is appropriate
when:

- provider SMTP submission is unavailable to the deployment;
- the provider's SMTP auth policy is harder to operate safely than OAuth;
- Gmail API quota/error reporting is preferred for that account;
- a future provider implementation needs API-only semantics.

Gmail API send requires adding only `https://www.googleapis.com/auth/gmail.send`
to the account's granted scopes. It must not require `gmail.modify` or the broad
`https://mail.google.com/` scope unless a separate future decision deliberately
adds provider mailbox mutation.

The API sender should submit raw RFC822 bytes generated by hail/Stalwart rather
than reconstructing message content from provider JSON. The generated message
must include stable dedupe headers described below.

## Source-of-truth rules

| State | Source of truth | Rule |
| --- | --- | --- |
| Composed message content before submission | hail-api/Stalwart send primitive | hail validates structured client input and builds MIME server-side. |
| Local Sent view, thread membership, message bodies, attachments | Stalwart | The hail UI reads local Stalwart/JMAP state only. |
| Provider SMTP/API delivery acceptance | Provider submission service | Provider response proves egress acceptance, not local UI truth. |
| Outbound retry/idempotency state | `hail.db` | Store operation ids, provider account binding, attempt status, backoff, safe error class, and provider response ids. |
| Provider-created sent copy | Provider mailbox until imported | If seen by import, dedupe/map to local sent object or skip; do not display as an extra message. |
| Provider labels/read/archive/delete state | Provider | Not written by hail in v1.2 provider import mode; provider labels/history may only bound read-only import scans. |

The invariant is: **a sent message visible in hail is the Stalwart object**. A
provider copy may exist for the provider's own Sent mailbox and audit trail, but
it does not replace or override local Stalwart state. Provider Sent labels,
read/unread flags, archive state, Trash, and deletion state remain provider-side
facts and are not mirrored back into hail except through explicit read-only
sent-copy dedupe decisions.

## Sent-copy dedupe policy

Provider send paths can create a second copy in the provider's Sent mailbox. The
importer must prevent that from appearing as a duplicate outbound message in
hail.

### Stable outbound identifiers

Every outbound message sent in provider import mode should include stable
headers before SMTP/API submission:

- RFC822 `Message-ID` generated once and reused across retries;
- `X-Hail-Outbound-Id` with a random, non-secret UUID/ULID for the outbound
  operation;
- optional `X-Hail-Provider-Account` containing an internal account id only if it
  is not sensitive in the operator's threat model; otherwise keep the mapping in
  `hail.db` only.

`X-Hail-Outbound-Id` is not an authentication secret. It is a correlation and
idempotency signal. Do not encode tokens, user emails, or database secrets in it.

### Mapping and duplicate detection

`hail.db` should record outbound mappings alongside provider import mappings:

- hail user/JMAP account id;
- provider account id and provider kind;
- outbound operation id (`X-Hail-Outbound-Id`);
- local Stalwart/JMAP message id and thread/mailbox ids when known;
- RFC822 `Message-ID` and optional content hash;
- provider SMTP/API response id, Gmail message id/thread id when available;
- status (`local_created`, `submitted`, `accepted`, `retrying`, `failed`,
  `deduped_provider_sent_copy`);
- timestamps and safe error class/message.

When the provider importer later sees a Sent message, dedupe in this order:

1. exact provider message id already mapped to an outbound operation;
2. `X-Hail-Outbound-Id` header matches an outbound operation;
3. RFC822 `Message-ID` matches a local sent object for the same user/account;
4. conservative content-hash match within a send-time window.

Matches should update the mapping/status and skip creating a visible duplicate.
Use `import_status='duplicate'` for proven provider Sent copies, with
`error_class` reused as a safe reason-class field rather than an error. The
standard reason classes are:

- `provider_message_already_mapped` — this provider message id already has a
  mapping, so importer replay is a no-op;
- `local_sent_message_id_match` — the provider Sent copy's RFC822 `Message-ID`
  matched a local Stalwart Sent object for the same provider account/user;
- `existing_local_message_id_match` — another localized provider mapping already
  points at the same local JMAP message for that RFC822 `Message-ID`;
- `no_local_sent_match` — no safe local sent-copy match was proven, so normal
  import may proceed.

Reason messages must be UI/log safe and must not include raw RFC822, message
bodies, tokens, SMTP credentials, or recipient lists. If the importer cannot
prove a match, it may import the provider message as a normal message, but tests
should cover the common Gmail SMTP/API sent-copy cases so this is rare and
observable.

## Failure, retry, and idempotency

Outbound has two durable effects: local sent state and provider delivery
acceptance. Treat it as a small state machine rather than a single fire-and-forget
call.

Recommended state order:

1. Create an outbound operation row in `hail.db` with an idempotency key.
2. Generate or persist the stable RFC822 `Message-ID` and `X-Hail-Outbound-Id`.
3. Create the local Stalwart sent object/submission record, or recover the
   existing one on retry.
4. Submit through Stalwart smarthost or Gmail API.
5. Record provider acceptance metadata and final status.
6. Dedupe any provider-created sent copy during later import.

Retry rules:

- retry transient network, TLS, DNS, provider 4xx-rate-limit/5xx, and Stalwart
  temporary submission errors with exponential backoff and jitter;
- honor provider `Retry-After` and SMTP enhanced status codes where available;
- classify auth/revocation, invalid recipient, message-too-large, malformed MIME,
  and policy rejection as permanent or operator-action errors;
- never regenerate `Message-ID` or `X-Hail-Outbound-Id` for the same logical
  outbound operation;
- do not hot-loop failed accounts; pause or degrade the provider account after
  repeated auth/quota failures;
- make retries cancellation-aware in `hail-worker` and safe after crashes.

If local sent creation succeeds but provider submission fails permanently, hail
should keep the local sent/draft/submission failure state visible and expose a
safe error. It must not silently delete the local sent object. A future UI may
offer resend, but resend should create a new explicit attempt or reuse the same
operation only when that is safe and visible to the user.

If provider acceptance succeeds but hail crashes before recording it, a retry may
risk duplicate delivery. Mitigations are provider-dependent: Gmail API response
ids should be persisted immediately; SMTP cannot generally provide exactly-once
delivery. The UI/status model should therefore say "accepted by provider" only
after durable recording, and smarthost retries after uncertain acceptance should
be conservative and operator-visible.

## Required configuration

Provider import outbound needs account-level configuration in addition to the
normal hail/Stalwart configuration.

### Global/operator config

- outbound mode per provider account: `stalwart_smarthost` (default) or
  `gmail_api_send`;
- whether provider-created Sent copies should be imported-and-mapped or skipped
  after dedupe;
- maximum message size for provider submission;
- retry/backoff limits and account pause thresholds;
- safe status/audit log retention.

### Stalwart smarthost config

For the preferred path, Stalwart needs provider SMTP submission settings:

- submission host, port, and TLS mode (`STARTTLS` or implicit TLS as required);
- authenticated provider username/from identity;
- SMTP credential source or OAuth/SASL mechanism if supported by the provider;
- envelope sender/from-address policy;
- provider-specific DKIM/SPF/DMARC guidance in the operator runbook;
- route selection so provider-import accounts relay through the matching
  provider account rather than a global default when multi-user is enabled.

Credentials must be stored in Stalwart/operator secret configuration, not in the
SPA. If hail stores or provisions smarthost credentials in the future, they must
use the same encrypted-at-rest posture as provider OAuth refresh tokens.

### Deploy examples

The checked-in base Stalwart config deliberately does **not** enable a provider
relay. Normal self-hosted/non-provider deployments continue to use Stalwart's
existing outbound defaults or whatever the operator configures in the Stalwart
WebUI. Provider import mode operators can opt in by copying one of these example
snippets into their private Stalwart configuration:

- `deploy/stalwart-provider-gmail-smarthost.example.toml` for Gmail SMTP
  submission at `smtp.gmail.com:587` with STARTTLS;
- `deploy/stalwart-provider-generic-smarthost.example.toml` for a generic SMTP
  relay on port 587 with STARTTLS.

Both snippets define a local route plus a provider relay route and select routes
with a Stalwart outbound expression:

```toml
[queue.strategy]
route = [
  { if = "is_local_domain('', rcpt_domain)", then = "'local'" },
  { else = "'provider-smtp'" },
]
```

That shape is intentional: local-domain recipients stay inside Stalwart, while
external recipients are relayed through the configured provider. Do not set the
route expression to always return the relay id, because that can loop or leak
local delivery through the provider.

Provider SMTP secrets are environment placeholders, for example:

```toml
[queue.route."provider-smtp".auth]
username = "%{env:HAIL_PROVIDER_SMTP_USERNAME}%"
secret = "%{env:HAIL_PROVIDER_SMTP_SECRET}%"
```

When using Compose, add `deploy/docker-compose.provider-smarthost.yml` as an
explicit overlay and put real values in an uncommitted `deploy/.env` file or in
your secret manager. `deploy/.env.example` documents the variable names with
redacted placeholders only. Logs, screenshots, task notes, and support bundles
must redact `HAIL_PROVIDER_SMTP_SECRET` and should redact SMTP usernames when
they contain private email addresses.

For Gmail, use `HAIL_PROVIDER_SMTP_USERNAME=you@gmail.com` (or a configured
send-as identity) and a Gmail app password or Workspace-approved SMTP relay
credential in `HAIL_PROVIDER_SMTP_SECRET`; never commit or document the real
value. For generic relays, set `HAIL_PROVIDER_SMTP_HOST` to the provider host and
use the provider-issued SMTP username/password or API key. If the relay requires
implicit TLS on 465, copy the generic example and set `port = 465` plus
`implicit = true` in the private config.

Stalwart v0.16+ also exposes these settings as MTA outbound Route/Strategy
objects in the WebUI. If the operator edits the WebUI instead of TOML, keep the
same semantics: a `Local` route for local domains, a `Relay` route for the
provider, STARTTLS/implicit TLS matching provider policy, auth secret sourced
from operator secrets, and no open-relay broadening beyond authenticated Stalwart
submission.

### Gmail API send config

For Gmail API send, hail needs:

- provider account row with `gmail.send` granted;
- encrypted refresh token and server-side token refresh;
- sender identity validation against the connected Gmail account or configured
  Gmail send-as alias;
- quota/backoff settings and Gmail error classification;
- a durable outbound operation table/mapping for idempotency and sent-copy
  dedupe.

The browser may request "send this message" through hail's normal API. It must
never receive Gmail access tokens or call Gmail directly.

## Security notes

- Keep OAuth refresh tokens encrypted in `hail.db`; keep access tokens only in
  process memory and never return them to the SPA.
- Do not log SMTP passwords, OAuth tokens, raw RFC822, message bodies,
  attachment content, or full recipient lists. Logs may include operation ids,
  provider account ids, local ids, error classes, and coarse status.
- Treat smarthost credentials as provider-account secrets. Prefer operator
  secret files/environment over checked-in config.
- Validate that the user can send as the selected From address. Provider import
  mode must not become an open relay for arbitrary sender identities.
- Preserve server-side MIME construction and sanitation; the SPA sends structured
  compose input, not arbitrary trusted RFC822.
- Add `gmail.send` only for accounts that actually use Gmail API send. Continue
  avoiding `gmail.modify` and broad Gmail scopes for v1.2 one-way import.
- Audit outbound actions without storing message content: who sent, through which
  provider account, when, final status, and safe error class.
- Make disconnect/revoke disable future provider sends for that account and
  clear/retire usable tokens according to the token crypto policy.

## Smoke and test expectations

Before enabling provider outbound in a release, add tests/smoke coverage for:

- Stalwart smarthost configuration and route selection;
- Gmail API send with fake HTTP responses and token sources;
- retries preserving `Message-ID` and `X-Hail-Outbound-Id`;
- dedupe of provider Sent copies imported after SMTP/API send;
- auth revocation/quota failures surfacing safe account status;
- no duplicate visible outbound messages in a thread after importer replay.

The human smoke should send through a real connected provider account, confirm
recipient delivery, then confirm hail shows one sent message in the local thread
after provider import catches up.
